# AI Agent Workbench 改进过程与当前进度

更新日期：2026-10-21  
依据：Git 提交记录、现有实现、工作进度记录及实际使用反馈。

本文按实施顺序整理项目从最初原型到当前版本的演进，解释每次为什么改、改了什么、留下什么问题。部分阶段在同一天连续实施，采用阶段编号，不推测不存在的日期。最新工作区包含尚未提交的修改；历史测试数字不是本次重新执行的测试结果。

## 1. 当前结论

项目已经从两个演示 Agent，发展为支持配置 Agent、MCP 工具、知识库、版本化 Skill、生成能力包和本地业务数据的个人 AI 工作台。

招聘场景经历了自动操作浏览器、统一任务流程、整表引擎、半自动填表的试验，真实网站效果没有达到预期。当前已收缩为：

> 用户提供岗位和资料 → 助手只读查看网页与表单 → 按审阅过的资料生成资料包 → 用户逐项复制、填写并提交 → 在本地台账维护投递阶段和日程。

当前资料包链路不替用户填写或提交招聘网站。通用受控浏览器仍有独立的人工审批操作能力，不能与已经撤下的自动投递功能混为一谈。

当前最突出的问题由“自动化兼容性”转为“长会话与工具结果带来的 token 消耗”。已完成代码检查，尚未实现主动摘要和上下文切换。

## 2. 阶段一：先打通对话与业务演示

### 目标与实现

- 建立 React 前端、FastAPI 后端与 Claude Agent SDK 的对话通路。
- 支持 Agent 选择、SSE 流式回答、会话及消息保存。
- 完成工时助理的受控 CLI 草稿、确认、取消与审计。
- 完成制度助理的 MCP 文档查询。

### 带来的改进

项目从只有模型聊天，变成可以调用工具、展示执行结果并让用户确认操作的业务原型。Agent 的配置与工具范围开始分离，执行权限由服务端控制。

### 当时的边界

工时等企业数据用于演示，不能据此声称已连接真实企业系统。此时以预置 Agent 为主，用户扩展能力有限。

提交锚点：`3e28a05`（M1）、`a71d648`（M2）、`fd66962`（M3）。

## 3. 阶段二：完善工作台、配置与运行环境

### 发现的问题

只有固定演示流程，新增 Agent 依赖改代码；历史会话切换、流式状态、审批重复点击等交互需要收口；换机器部署不够方便。

### 改进

- 完善会话切换和状态恢复，前后端按职责分层。
- 增加 Docker Compose 开发环境与数据持久化说明。
- 页面创建自定义 Agent，连接 HTTP/SSE MCP、发现工具定义、选择工具白名单。
- 条件更新防止同一审批重复执行；工具调用进入审计记录。

### 结果

用户可以通过配置装配业务 Agent，而不必为每个新场景重写工作台。数据库、SDK 会话、凭证仍是运行数据，需要单独备份，Git 不能替代运行数据迁移。

提交锚点：`9027847`、`8be095f`、`6fcb0ff`、`8cde210`。

## 4. 阶段三：知识库、来源引用与检索评估

### 目标

让问答有可追溯资料，区分模型回答与实际检索证据，能够回看和评估检索结果。

### 改进

- 增加多知识库、MD/TXT 入库、更新、版本与删除。
- SQLite FTS5 关键词检索及 BM25 排序，合并重叠命中片段。
- Markdown 按相邻标题块切分，普通文本回退到字符切分。
- Agent 绑定知识库，调用时检查可访问范围。
- 回答保留引用、版本、行号和来源快照，支持原文预览与定位。
- 区分未检索、无匹配、检索失败和找到资料。
- 增加批量检索评估、耗时和报告导出。
- 独立笔记 MCP 增加只读访问、认证和来源展示。

### 结果与边界

回答依据比单纯聊天更容易核验，但引用存在不等于结论正确。目前仍是关键词检索，没有向量检索、Embedding 或混合检索；是否调用检索仍取决于模型。

提交锚点：`3288750`、`2c1e4bc`、`2969eab`、`2c0a3e7`。

## 5. 阶段四：Skill 版本化与按需加载

### 发现的问题

把所有工作方法都塞进提示词会变长，方法更新也可能影响已有 Agent；简单限制绑定数量无法准确控制上下文开销。

### 改进

- 网页创建、编辑、导入导出 Skill，并支持 Markdown 预览。
- 保存历史版本，Agent 固定绑定版本，可以主动切换。
- 模型先看到用途目录，需要时才读取正文。
- 从固定的绑定数量限制改为每轮实际读取字符预算。
- 大目录可搜索与分页，回答记录本轮实际读取过的版本。

### 结果与遗留

减少了每轮无差别注入方法正文的问题。但读取后的正文仍可能保留在 SDK 会话里，所以“按需读取”尚不能代替长会话压缩。

提交锚点：`daec111`、`a56f952`、`01ab081`、`c664273`。

## 6. 阶段五：构建助手与生成能力包

### 目标

让用户描述需求后，由平台创建 Agent 及其所需的数据处理方法。

### 改进

- 构建助手澄清需求、生成纯数据 Python 方法、运行独立测试、失败修正。
- 发布前经用户审阅，形成独立 MCP 能力包。
- 能力包版本不可变，Agent 固定绑定，旧版本不被静默替换。
- 构建时查找已有 Skill、按需读正文、说明复用理由；缺失 Skill 可先生成草稿，用户保存后入库。

### 结果与边界

形成“描述需求 → 编写方法 → 测试 → 审阅发布 → 切换使用”的闭环。生成范围仍是受限的数据处理方法，不代表可以任意生成具备邮箱或网站写入权限的连接器，也没有实现主副 Agent 团队编排。

提交锚点：`4b8fcd1`，后续复用与测试见构建助手文档。

## 7. 阶段六：附件、公开网络、浏览器与持久跟踪

### 新增能力

- 会话附件与 PDF/DOCX、文本解析。
- 公开网页搜索和正文读取。
- 独立浏览器、网页快照、预览、用户接手登录，以及人工审阅后的操作。
- 文件固定 ID、版本、哈希、本机单文件关联与重新关联。
- 执行记录、工作事项、只读定时状态检查和站内未读提示。

### 使用中连续修复的问题

| 实际问题 | 改进 |
| --- | --- |
| 大页面截断导致上传入口“消失” | 完整快照保存在平台，向模型分页、查找，保留跨帧引用 |
| 空白标签被误判为未登录或跨站 | 识别标签与页面状态，复用已有页面，避免丢失填写现场 |
| 焦点或样式变化让操作清单失效 | 使用语义指纹，截图预览与执行资格分开 |
| 点击成功，跳转后的读取失败却报操作失败 | 分开记录执行与后续读取，页面未就绪时提示核对 |
| 审批异常后按钮仍可重复点击 | 补读服务端持久状态，防连点、过期禁用，迟到事件不能覆盖终态 |
| 下拉浮层遮挡后续字段 | 增加可审阅的 Esc 操作及可读错误原因 |
| 历史 SDK 会话文件缺失 | 在尚未返回任何 SDK 消息时，限一次使用近期聊天重建，防止重放写操作 |

### 结果

浏览器可观察性和会话恢复有所改善，但这些改进主要解决“能读、能确认、能追踪”，尚不足以保证复杂招聘表单能全自动完成。

提交锚点：`4ce385d`，后续本机浏览器和跟踪成果归入 `b867b7e`。

## 8. 阶段七：自动投递试验与路线调整

### 8.1 通用任务模型及单 Agent 闭环（历史实施，当前已撤下）

曾实现任务、步骤、尝试与事件模型，加入状态机、防重、固定版本资料、执行意图、结果未知核对、重启恢复和提交审批。合成网站验收过填写、上传、回执入账，最终提交由用户确认。

P0 历史测试记录为后端 318 项；P1 为后端 322 项、前端 80 项，后端各有 5 项环境依赖跳过。它们证明当时相应合成链路成立，不证明真实招聘站点通用可用。

### 8.2 从逐批确认改为最终确认（历史实施，当前已撤下）

真实操作中确认过多。曾增加任务级自动填写授权，限定目标网站，填写和非提交操作直接执行，最终提交单独审阅；确认栏改为只显示当前请求，其余进入历史请求。

但 Agent 大量绕过任务流程，仍用普通浏览器逐步点击。一次会话累计出现 48 条操作确认，45 条只有一个动作，并读取网页 106 次。该统计覆盖这次尝试中的多轮操作，不是单次模型回复。

### 8.3 表单引擎试验（历史实施，当前已撤下）

为降低模型逐个点击的成本，曾增加整表结构提取、字段与资料映射、自定义下拉、级联、日期等适配器，以及字段读回和最终总表。

合成站点验收实现“回答一次问卷、最终确认一次提交”。过程中发现日期输入后按回车会提前提交，随后移除回车并增加页面跳转即停的保护。

历史测试记录为后端 333 项（5 项跳过）、前端 83 项。这里的覆盖主要来自本机合成页面，本机 Chrome 路径和真实厂商控件仍有覆盖差距。

### 8.4 真实站点暴露的限制

北森表单实测中，下拉与上传入口未被完整识别，46 个字段主要被当作文本字段；字段标签误取成“请输入”，必填识别不足。逐步点击的后置条件过弱，仅凭页面地址存在就记成功，不能证明选中值实际保存。

这说明测试页过度贴近实现假设，验收只证明已知结构可用。“点击已完成”“字段值已保存”“业务已提交”必须分开判断。

### 8.5 A+B 半自动流程（历史实施，当前已撤下）

按用户选择，曾调整为先上传简历让网站解析、平台补文本、下拉失败后交给用户，提交前整表重新读回与纠错；同时修复新写入工具审计日志的部分个人标识脱敏。

历史测试记录为后端 337 项（5 项跳过）、前端 84 项。北森真实页面尚未完成复测，旧审计明文也没有因此自动清理。

### 8.6 最终收缩：资料包与投递台账（当前方案）

用户随后决定撤下自动投递。任务框架和网申自动写入链路退出当前产品流程，源码按既有记录归档到本地运行目录。

保留并建设：

- 投递台账：公司、岗位、链接、截止日期、阶段、日程、提醒与变更记录。
- 资料档案：使用用户审阅保存的版本。
- 只读读表：按页面顺序提取字段及当前值，不展开和填写控件。
- 资料包：给出字段建议值、来源、转换与草稿标记；用户逐项复制、修改并自行提交。
- 缺失必填项单独列出，不补造事实；助手不能自行推断已投递。

历史验收记录为后端 316 项（5 项环境依赖跳过）、前端 80 项及生产构建通过。数量减少来自功能移除及测试范围变化，不表示质量倒退。最新工作区还有界面及样式修改，本次文档整理没有重新执行完整测试。

## 10. 最新问题：token 消耗与上下文策略

2026-10-21 对更新后的代码做了只读检查，结论如下。

### 已有措施

- 浏览器快照支持分页、关键词查询，默认返回 12,000 字符正文和 80 个元素，仍可能同时返回相同信息的两种表示。
- Skill 先目录后正文，控制当轮读取字符量。
- SDK 会话恢复失败时最多注入 24 条、30,000 字符近期聊天；这不是正常长会话的自动压缩。
- 资料包生成只返回保存结果、条目数及缺失项摘要；台账列表已经不附资料包正文，但尚无列表分页。

### 主要缺口

- 正常对话通过 SDK `resume` 延续历史，没有平台维护的摘要检查点与新模型会话切换。
- 读取资料工具会一次返回所有已审阅档案正文；较长工具结果随会话累积。
- SDK 返回 `usage`、`model_usage` 等字段，但当前运行时代码未持久化或展示。
- SDK 有自动压缩相关机制，当前平台没有记录其启用情况、触发时点和效果，不能承诺已生效。

### 建议实施顺序（尚未实施）

1. 记录输入、输出、缓存用量及工具调用次数，计费字段按模型服务实际提供情况展示。
2. 缩小默认工具结果：资料目录与正文分离、台账分页、网页精简返回与按需展开。
3. 引入工作摘要和近期消息窗口，在检查点切换新的模型会话；前端保留完整聊天记录。
4. 按岗位隔离工作上下文，以本地台账和固定版本资料为长期事实来源。

摘要必须保留目标、用户要求、资料版本、待办、结果未知事项和记录 ID，不能把历史操作意图变成新的授权。单纯追加摘要而继续携带全部旧上下文，无法达到节省效果。

## 11. 阶段八：多 Agent 协作与真实模型验收（2026-10-28）

### 目标与实现

负责人 Agent 按需组建团队：可以委派现有 Agent，也可以创建临时 Agent（能力不超过负责人自己）。需要多名成员或讨论时，先提交团队计划，由用户在确认卡里调整成员、说明和能力后批准。协作方式有两种，由负责人按任务选择：`delegate`（分头完成）和 `discuss`（成员轮流发言、互相看到原文）。成员在各自的子会话里运行，不能再委派。分支 `codex/agent-teams`。

### 真实模型验收发现的问题与改进

验收在隔离副本中进行（临时数据库、检查点和文件目录），任务为“组团评审：审批人批量通过报销单”。

| 实际问题 | 原因 | 改进 | 提交 |
| --- | --- | --- | --- |
| 成员回复约 1.2 万 token，超过 8000 字被截断 | 成员不知道截断上限 | 平台在任务末尾附篇幅要求（委派 5000 字、发言 2000 字）；卡片只显示负责人写的原文 | `c840231` |
| 临时 Agent 名字是 `security_reviewer` 这类标识符 | 模型习惯 | 提示词和工具说明要求简短中文名；校验拒绝标识符形式的名字 | `c840231` |
| 负责人 3 次调用输入 14.7 万 token | `langchain_deepseek` 用 `json.dumps` 发送列表形式的工具结果，未设 `ensure_ascii=False`，中文变成 `\uXXXX`，约 6 倍 token；影响所有工具 | 只含文本块的工具结果拼成纯文本再发送 | `c9b2a14` |
| 讨论发言 4 次中 3 次被截断，负责人额外委派一次补齐 | 要求 2000 字，模型实际写 3,500–3,700 字，超过 3000 字上限 | 发言上限 3000 → 6000 字，讨论记录合计 12000 → 24000 字；要求篇幅不变 | 见下 |

### 复测结果（同一任务）

| 指标 | 修复前 | 前三项改进后 | 四项改进后 |
| --- | --- | --- | --- |
| 负责人输入（批准后那一轮） | 147,210（3 次调用） | 77,398（4 次调用，−47%） | 36,641（3 次调用） |
| 其中未命中缓存 | 84,490 | 26,454（−69%） | 18,593 |
| 全流程输入合计 | 243,898 | 154,607（−37%） | 85,215 |
| 全流程输出合计 | 59,646 | 43,811 | 24,378 |
| 讨论发言被截断 | — | 4 次中 3 次，额外委派 1 次补齐 | 0 次，无补齐 |
| 耗时 | 369 秒 | 295 秒 | 173 秒 |

前三项改进后，负责人的 4 次调用里有 1 次是为补齐被截断的发言，第四项改进正是为此。第四项改进后复测（2026-10-29）：没有截断，也没有补齐委派。但这次 4 次发言为 1,939–2,761 字，都在旧上限 3000 字以内，所以这次复测没有真正考验新上限，新上限由离线测试覆盖（发言写到要求的 2 倍时完整传给负责人和下一位成员）。第三次的总量明显更低，主要是模型这次写得更短（委派回复 3,223 / 4,075 字，上次 6,102 / 7,325 字），属于单次运行的波动，不能都算作改进效果。

### 遗留

- 委派成员的工具调用偏多：研究员一次委派用了 19 次工具调用、13.4 万输入。
- 成员达到工具上限（提交 `82e2f6c`）：不另设更低上限——成员停下后用户无法在子会话里让它继续。成员达到全局单轮上限（默认 25 次）时，提示改为“先写已核实的结论，再列出没完成的部分”，委派结果带 `tool_limit_reached` 标记并提示负责人可以再委派同一成员“继续”；子会话保留成员的进度，不必重新交代背景。仅离线测试。
- 组团协作的成本约为负责人单独回答的数十倍，适合需要多视角的任务；简单问题负责人会直接回答，不组团。
