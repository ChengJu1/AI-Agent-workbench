# 里程碑 3：MCP、Skills 与完整业务演示闭环

## 周期与验收要求

- 周期：第五周到第六周。
- 验收要求：建议在第六周结束前完成里程碑验收。
- 验收方式：全流程功能演示 + 代码走读 + 演示脚本检查。

## 阶段目标

在 M2 的基础上接入 MCP 工具和第二个业务 Agent，形成完整演示闭环。

本阶段结束后，系统应能稳定演示：

1. 在 Web 页面选择工时助理，完成 CLI 工具调用和人工确认。
2. 在 Web 页面选择制度信息 QA Agent，通过 MCP 或 Skills 查询制度信息。
3. 查看工具调用日志和关键错误信息。

## 设计思路

M3 不追求接入真实内部系统，而是通过本地 mock MCP server 展示系统扩展方式。MCP server 可以提供内部制度查询、资源目录查询或申请模板查询等能力。

推荐优先实现“制度信息 QA Agent”，因为它比真实审批 Agent 更容易控制边界：

1. 制度内容使用本地 Markdown mock 文档。
2. MCP 工具提供 `search_policy` 或 `get_policy_detail`。
3. Agent 回答时必须说明依据来自哪条制度。
4. 不确定时要求用户补充信息或提示转人工。

权限申请辅助 Agent 可以作为配置样例或扩展任务，不作为 M3 必须交付。

## 模块与目的

1. MCP Adapter 模块  
目的：验证系统可以通过配置接入 MCP 工具，而不只支持 CLI。

2. 制度信息 QA Agent  
目的：提供第二个业务 Agent，证明 Agent Workbench 不是单一工时助手。

3. Skills 管理模块  
目的：将业务规则、回答边界、操作规程从代码中拆出。

4. 日志与错误处理模块  
目的：让演示过程中工具调用失败、MCP 启动失败或参数缺失时有可理解反馈。

5. 演示脚本模块  
目的：沉淀可复现的项目展示路径，为 M4 复盘和模拟面试做准备。

## 交付物

1. 本地 mock MCP server。
2. MCP 工具接入配置。
3. 第二个业务 Agent 配置，优先选择 `policy_qa_assistant` 制度信息 QA 助理。
4. 制度信息 mock 文档或 Skill 文档。
5. Agent 回答来源引用规则。
6. 工具调用日志查询接口或日志展示页面。
7. 错误处理与兜底提示。
8. “如何新增一个 Agent”的简短说明文档。
9. M3 全流程演示脚本。

## 任务拆解

1. MCP server
   - 实现最小本地 MCP server。
   - 提供 `search_policy` 工具。
   - 提供固定 mock 制度数据。
   - 保证本地启动稳定。

2. MCP 接入
   - 在 Agent manifest 中声明 MCP server。
   - Claude Runtime 根据 Agent 配置加载 MCP 工具。
   - 处理 MCP 启动失败和调用失败。

3. 制度信息 QA Agent
   - 编写 `policy_qa_assistant` 配置。
   - 编写系统提示词。
   - 编写制度 QA Skill。
   - 要求回答带制度来源或说明无法确定。

4. 日志与错误处理
   - 增加工具调用状态展示。
   - 增加后端日志查询接口，或在页面展示最近调用记录。
   - 对 CLI/MCP 错误返回友好提示。

5. 演示闭环
   - 准备工时助理成功路径。
   - 准备工时助理取消提交路径。
   - 准备制度 QA 成功查询路径。
   - 准备制度 QA 无答案兜底路径。

## 验收标准

1. 页面能选择至少两个 Agent。
2. 工时助理能完成 M2 的 CLI 与人工确认流程。
3. 制度信息 QA Agent 能调用 MCP 工具查询制度。
4. 制度信息 QA Agent 的回答带来源说明。
5. 工具调用失败时有明确错误提示。
6. 审计日志能区分 CLI 调用和 MCP 调用。
7. 导师可以按演示脚本复现完整流程。

## 明确不做

1. 不做真实制度库接入。
2. 不做复杂向量检索平台。
3. 不做真实权限申请提交。
4. 不做多个 MCP server 的复杂管理页面。
5. 不做生产环境部署。
