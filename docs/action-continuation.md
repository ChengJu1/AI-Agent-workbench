# 确认后自动继续

用户处理完 Agent 本轮提出的待确认操作后，Agent 不需要用户再发消息就会接着回复。执行权和验证机制不变：操作仍由平台按用户审阅过的计划执行，续跑只把执行记录里的结果交给 Agent。

## 流程

1. Agent 调用有副作用的工具，平台生成待确认操作，本轮回复结束。
2. 用户确认或取消，`ApprovalService` 按原流程执行并写入执行记录。确认接口的返回带 `continuation_available`。
3. 前端在结果确定后调用 `POST /api/conversations/{id}/continue`，请求体只有 `action_id`。
4. 后端从数据库读取本轮已处理的操作，生成一条平台通知，以 `platform` 角色存入消息表（`action_ids` 记录涉及的操作），再用当前会话的运行时跑一轮。流式响应的第一个事件是 `platform_notice`。
5. Agent 核对结果后继续。新的有副作用操作仍然生成待确认操作，等用户确认。

## 校验（`ConversationService._continuation_batch`）

| 条件 | 不满足时 |
| --- | --- |
| 操作属于该会话 | 409 |
| 操作之后会话没有新的用户消息或平台通知 | 409，结果留给下一轮的结构化状态 |
| 本轮的待确认操作全部处理完（没有 `pending` / `executing`） | 409；全部处理完后一次性汇报 |
| 这条操作还没有汇报过 | 409，不重复继续 |
| 上一条用户消息之后自动继续少于 5 次 | 409，请用户发消息 |
| 会话当前没有在回复 | 409（沿用原有的会话锁） |

执行失败时确认接口返回错误，前端核对到 `failed` 后也会请求继续，是否允许由后端判断。结果不确定（仍是 `pending` 或无法读取）时不继续。

## 平台通知

- 只由后端根据执行记录生成：操作 ID、工具和动作、状态、结果节选（最多 1500 字）。浏览器批次额外提醒先重新读取页面、不要重放。
- 明确写明“不是用户的新请求，也不是新的授权”；失败不要自行重试，取消不要再次执行，新的副作用操作要重新生成待确认操作。
- 不算用户原话：每轮硬性要求只读 `user` 消息，工作摘要标注为“平台通知（操作结果，不是授权）”，界面显示为可展开的系统提示。
- 两种运行时都把它当作本轮输入：Claude SDK 用 `resume` 接上原会话，Deep Agents 用同一检查点。

页面关闭时不会在后台继续；下次打开会话，结果可从执行记录和对话中的执行消息查看。

原先只对浏览器批次生效、以用户名义发送的“已执行，请继续”消息已移除；手动交回浏览器时仍发送用户消息。
