# 知识库建立与文档检索

知识库入口位于聊天页面工具栏。第一版完成文档管理、分段入库和关键词检索验证，为后续 RAG 问答提供可复用的原文和来源数据。

## 使用方法

1. 重启后端，刷新前端页面，点击“知识库”。后端启动时会自动增加所需表和索引，保留已有会话及 Agent 配置。
2. 填写知识库名称和可选说明，点击“创建知识库”。一个工作台可以建立多个知识库。
3. 选择知识库并上传文件。支持 UTF-8 编码的 `.md`、`.markdown`、`.txt`，以及 `.pdf`、`.docx`，单文件最大 2 MB，可一次选择多个文件。PDF/DOCX 在沙箱中提取文字后按纯文本保存（不保留排版，DOCX 表格附在正文后），PDF 最多 40 页；扫描版 PDF 没有文字层会被拒绝，提取文字超过 12 万字也会被拒绝而不是截断。
4. 上传后自动解析、分段并建立索引。页面显示每个文件的入库结果、版本和片段数量。
5. 点击“预览分段”查看原文片段、所属章节和行号；在“检索测试”输入文档中的关键词检查检索结果。
6. 展开“批量检索评估”，运行已知题目并查看失败案例，可导入自己的 JSON 题集和导出报告。见 [批量检索评估](./retrieval-evaluation.md)。

文档同名且内容相同时不重复入库；同名内容变化时更新为下一版本并替换原索引。不同知识库的文档互不覆盖。删除文档或知识库时，相关分段与索引一并清理，不删除用户电脑上的原始文件。

需要演示资料时，可使用 [知识库示例文档与通用模板](./knowledge-samples/README.md)，其中附有可直接上传的文档和检索词。

## 实现与存储

- 知识库、文档正文、版本和片段保存在当前工作台 SQLite 中，使用已有的 `WORKBENCH_DATABASE_PATH` 配置。
- Markdown 按文档级 H1–H6 标题建立块：从标题开始，到下一个标题之前结束，不同层级都作为边界；保留父级标题路径。每段包含两个相邻完整块，按 `A+B`、`B+C`、`C+D` 滑动，重叠一个完整标题块。
- 标题前的非空前言也作为一个块；只有一个块时只生成一个片段。超过 800 字符的标题块会在段落、换行或句子结尾处再切开（找不到时按 800 字符硬切），切出的部分沿用原标题，因此每个片段最多约 1600 字符。文档末尾不会再生成一个只重复末块的片段。
- 使用 Markdown 解析器识别 ATX（`#`）和 Setext（下划线）标题。围栏代码、缩进代码、列表、引用中的标题不作为文档边界；首部 YAML 元数据保留为前言。
- 无实际标题的 Markdown 和 TXT 使用字符分段作为回退：最多 800 个字符，优先在段落、换行或句子边界切分，相邻片段重叠 100 个字符（首尾空白会被裁剪）。
- 保留规范化文本的字符位置、起止行号及 Markdown 章节名。UTF-8 BOM 和 Windows 换行会在入库时统一处理。
- SQLite FTS5 保存本地关键词索引，中文采用单字与连续双字词，英文采用词条。查询按关键词匹配并排序，返回来源原文，不生成答案。
- 检索分关键词和向量两路，见下文“混合检索与相关度判断”。融合后的候选按同一文档、同一内容版本的字符区间合并重叠命中，再截取最多 5 组。`A+B` 与 `B+C` 合并为 `A+B+C`，正文从重叠位置拼接，只保留一份 B；不同文件、版本或不同位置的相同文字不删除。
- 合并组保留其中最高排名命中的位置与代表 ID，`source_chunk_ids` 记录已合并的全部片段 ID。只合并有实际交集的区间，不拼接分离的命中；起止字符、行号和原文保持对应。合并扩展上限为 4000 字符，超过时保留排名更高的组、忽略该重叠候选；单个已有长片段不截断。一次返回的原文合计不超过 10000 字符，超出部分按排名从后往前省略并记在 `diagnostics.omitted_for_length`。因此去重后结果可能少于请求上限。
- 文档、分段与索引在同一事务中写入。分段或索引失败时不发布半成品，替换失败会保留原有版本。
- 每份文档保存 `indexing_version` 和 `chunking_strategy`。后端启动时自动重建旧策略的分段和 FTS 索引，保留文档 ID、正文、内容版本、时间、Agent 绑定以及历史回答的引用快照；以后启动不重复重建。索引升级失败按文档回滚，可修复后重试。
- 第一版在上传请求中同步完成入库，处理中的状态显示在页面；成功后才进入已入库文档列表，不依赖后台任务队列。

## 混合检索与相关度判断

- **向量**：本地嵌入模型 `intfloat/multilingual-e5-large`（1024 维，fastembed 加载 ONNX 版，不依赖 torch）。每个片段以“章节 + 换行 + 正文”生成一次向量，归一化后以 float32 存在 `knowledge_chunk_vectors` 表；片段删除或重新切分时由触发器一并删除，换模型时旧向量整体作废、重建。入库后和后端启动时由后台线程补齐，不阻塞上传。
- **两路召回**：BM25 和向量余弦相似度各取返回上限 3 倍的候选（默认各 15 条）。向量在内存中逐个计算，几千个片段以内只需几毫秒。
- **融合**：倒数排名融合（RRF，k=60），一个片段的得分是它在每一路 1/(60 + 名次) 之和，只看名次，两路分数不需要可比。融合后再做上面的重叠合并和截取。
- **相关度判断（软判断）**：本地重排序模型 `BAAI/bge-reranker-v2-m3-int8` 只给合并后的前 3 组打分（每组取前 1000 字），**不改变顺序、不删除结果**。最高分低于 0.02 时 `diagnostics.low_relevance` 为真，结果附带 `notice`，提示 Agent 先核对片段是否真的回答了问题。评估中负例返回空结果或被标记为可能不相关都算判对。
- **排序明细**：每条结果的 `ranking` 记录关键词名次与 BM25 分、向量名次与余弦值、RRF 得分，前 3 组还有相关度；检索测试页和评估报告逐条显示。
- **退回**：模型文件需预先放在 `backend/data/models`（运行时只读本地文件，不联网下载）。嵌入模型不可用时只用关键词检索，`method` 为 `keyword`；重排序模型不可用时跳过相关度判断。`WORKBENCH_KNOWLEDGE_EMBEDDING_MODEL=none`、`WORKBENCH_KNOWLEDGE_RERANK_MODEL=none` 可分别关闭。
- **为什么只判断、不重排**：在 71 道本地评估题上，用重排序结果替换混合检索的顺序会让正例排第 1 从 37 道降到 31 道，每次检索多 4 秒；只看前 3 组判断相关度，正例不受影响，30 道负例判对 29 道，每次多约 0.8 秒。阈值只基于这一套题校准，余量不大（有正例的前 3 组最高分只有 0.022），换知识库后应重新评估。

SQLite 需支持 FTS5。文件上传依赖 `python-multipart`，Markdown 标题解析依赖 `markdown-it-py`，均已加入后端依赖清单；安装 `backend/requirements.txt` 或 `backend/requirements-dev.txt` 后重启后端即可升级。

## API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/knowledge-bases` | 创建知识库，JSON 字段 `name`、`description` |
| GET | `/api/knowledge-bases` | 列出知识库和文档、片段数量 |
| GET | `/api/knowledge-bases/{id}` | 知识库详情 |
| DELETE | `/api/knowledge-bases/{id}` | 删除知识库及其内容，成功返回 204 |
| POST | `/api/knowledge-bases/{id}/documents` | 上传文件，multipart 字段为 `file` |
| GET | `/api/knowledge-bases/{id}/documents` | 文档列表、版本及就绪状态 |
| DELETE | `/api/knowledge-bases/{id}/documents/{document_id}` | 删除文档及其索引，成功返回 204 |
| GET | `/api/knowledge-bases/{id}/documents/{document_id}/chunks` | 分段预览，支持 `offset`、`limit` |
| POST | `/api/knowledge-bases/{id}/search` | 关键词检索，JSON 字段 `query`、可选 `limit` |

新文件上传返回 201，文档更新或相同内容返回 200。响应为：

```json
{
  "document": {
    "id": "文档ID",
    "knowledge_base_id": "知识库ID",
    "filename": "policy.md",
    "byte_size": 415,
    "version": 1,
    "chunk_count": 1,
    "status": "ready",
    "indexing_version": "md-heading-overlap-v2",
    "chunking_strategy": "markdown_headings",
    "created_at": "创建时间",
    "updated_at": "更新时间"
  },
  "created": true,
  "unchanged": false
}
```

超限返回 413，不支持的格式返回 415，无效文件名、编码或空内容返回 422，不存在或不属于该知识库的文档返回 404。

检索结果包含 `method: "keyword"`、查询词和匹配片段。每个片段带有文件名、文档版本、章节、行号和原文。没有匹配时返回空数组。

检索测试会显示“候选 N 条 → 去重后 M 组 → 返回 K 组”及后端检索毫秒数。接口 `diagnostics` 包含 `candidate_count`、`unique_count`、`merge_limit_skipped`、`elapsed_ms` 和 `deduplication_ms`。`unique_count` 是截取结果上限之前的组数；`merge_limit_skipped` 表示因扩展上限忽略的重叠候选数。

耗时用单调时钟测量：`elapsed_ms` 包含候选 SQL 查询、BM25 排序、读取结果和去重；`deduplication_ms` 是其中的合并处理部分。不含分词、网络传输、页面渲染和模型回答时间，空结果也返回计时。页面在下一次检索开始时清除旧结果，避免旧耗时被误认成新查询结果。管理页、Agent 检索工具和批量评估共用相同检索实现。

此修改不重建索引，也不减少数据库中的重叠存储。候选扩展可能增加查询工作量；主要减少返回结果和模型上下文的重复，具体耗时以反馈为准。

## 当前范围和后续接入

文档管理和页面检索使用本地关键词索引和本地模型，不依赖模型密钥、在线 Embedding 服务或 LangChain。

Agent 已支持绑定知识库和调用检索工具，详见 [Agent 知识库绑定](./agent-knowledge.md)。在对话中调用工具时，匹配片段及其来源会作为工具结果传给当前配置的模型。仅上传文档或在管理页面测试检索，不会自动调用模型。

回答引用和原文快照已接入，见 [带引用的知识库问答](./knowledge-answers.md)。混合检索和相关度判断见上文。

知识库在当前工作台内共享；知识库 ID 的范围检查用于防止串库，不代表已经实现账号级权限隔离。

## 验证

自动化测试使用临时数据库，覆盖上传与恢复、版本替换、去重、中文英文检索、来源位置、跨库隔离、删除清理、并发重复上传以及索引失败回滚。页面联调使用临时数据库验证新建、真实文件上传、检索、分段预览和刷新后保留，不改动用户已有数据。

自动化验证还覆盖完整标题块重叠、各级标题和前言、Setext 标题、代码和引用中的伪标题、YAML 元数据、长章节不截断、旧库自动升级、重复启动、并发变更保护和重建失败回滚。
