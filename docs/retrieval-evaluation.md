# 批量检索评估

评估入口位于“知识库”管理页面的“批量检索评估”。它使用一组已知问题检查当前知识库的关键词检索，不调用模型，不修改文档或聊天记录。

## 使用

1. 选择“演示知识库 · 团队协作”，确保四份示例文档都已上传。
2. 展开“批量检索评估”，默认加载“团队协作示例题集 v1”，共 18 题。
3. 选择每题返回条数，默认 5，点击“运行评估”。
4. 查看通过数量、首条命中率、前 K 条命中率和空结果判断。默认展示失败与不适用题，切换“全部题目”可逐题核对。
5. 展开题目查看预期文件、关键原文、命中排名、实际片段及来源行号。
   每题也显示候选数、去重后组数、实际返回组数、检索与去重耗时；报告顶部显示整轮评估耗时和单题平均检索耗时。
6. 点击“导出报告”保存本次结果；报告仅在当前页面保留，关闭或刷新后可重新运行。

题集可导出为 JSON，修改后通过“导入自己的题集”加载。文件最大 100 KB，每次评估 1–50 题，每题返回 1–20 个片段。

## 题集内容

内置 [团队协作题集](../backend/evaluations/team-collaboration-v1.json) 包含 16 道正例、2 道空结果题，覆盖四份示例文档中的制度、工时、产品和排障信息。题型包括关键词、自然语言问句及“显卡”查 GPU 制度的同义词挑战。

正例必须同时指定预期文件和关键原文。多个关键原文需要在同一个返回片段中出现，避免两个缺失上下文的片段被误判为完整命中。原文按精确文本匹配，不使用模型判断语义等价。

空结果题必须返回零片段。它评估本次查询是否返回内容，不代表系统已具备通用的相关性拒答能力。

自定义题集示例：

```json
{
  "name": "我的制度题集",
  "description": "检查 GPU 制度和不存在的编号",
  "limit": 5,
  "cases": [
    {
      "id": "gpu-approval",
      "query": "GPU 申请",
      "category": "keyword",
      "expected_filename": "01-资源申请制度.md",
      "expected_texts": ["项目负责人和资源管理员共同审批"]
    },
    {
      "id": "missing-code",
      "query": "QZX987654ABC",
      "category": "negative",
      "expect_no_match": true
    }
  ]
}
```

`category` 可选 `keyword`、`question`、`paraphrase`、`negative`。判定是否为空结果题以 `expect_no_match` 为准；题目 ID 必须唯一。预期文件名需要与已上传文件完全一致。

## 判定和指标

- 正例通过：前 K 条中至少有一个片段来自预期文件，包含全部关键原文，且返回片段的原文位置、行号、版本与本次文档一致。
- 空结果题通过：没有返回任何片段。
- 不适用：预期文件未上传，或指定关键原文已不在该版本的文档中。报告明确提示不完整，不把这些题算作通过。
- 有效题通过率：通过题数 ÷ 有效题数，包含正例和空结果题。
- 首条命中率：第一条命中目标片段的正例数 ÷ 有效正例数。
- 前 K 条命中率：前 K 条内命中目标片段的正例数 ÷ 有效正例数。
- 空结果正确率：正确返回空结果的题数 ÷ 有效空结果题数。

无有效分母时指标为 `null`，页面显示“—”。命中率只衡量目标原文是否被召回，原文位置校验另行影响通过判定。指标不评价模型生成的答案是否正确，也不验证结论是否被引用支持。

## 字符分段历史基线

在四份示例资料、旧字符分段（800 / 100）、每题返回 5 条的条件下：

| 指标 | 结果 |
| --- | --- |
| 有效题通过 | 17 / 18（94.4%） |
| 正例首条命中 | 14 / 16（87.5%） |
| 正例前 5 条命中 | 15 / 16（93.8%） |
| 空结果正确 | 2 / 2（100%） |

失败题是“显卡”：预期命中 GPU 制度，当前词法索引无法把这个同义词映射到 GPU。该题保留在题集中，后续增加语义检索时使用同一题集比较，不为提高数字而移除失败题。这是一组小规模演示题，不能代表其他资料和问题的效果。

## 标题块分段复测

同样四份文档和原 18 题、每题返回 5 条，改为相邻两个标题块分段并重叠一块后，总片段由 8 个变为 24 个。有效题通过仍为 17 / 18，正例首条命中由 14 / 16 提升为 15 / 16（93.8%），前 5 条命中仍为 15 / 16，空结果题仍为 2 / 2。失败题仍为“显卡”，标题块切分不会赋予关键词索引同义词检索能力。文档内容版本保持 v1。

## 一致性和接口

一轮评估的全部查询、原文校验和版本清单共享 SQLite 读快照。评估过程中发生的文档更新不会混入本轮报告。复用正常检索的分词、MATCH 查询和 BM25 排序，避免评估器维护另一套检索实现。

评估与正常检索共用 `overlap_merge_v1` 处理：取 3 倍候选后合并重叠原文，合并扩展上限为 4000 字符，按组内最佳命中排名排序。前 K 条现在指去重后的结果组；组可以包含多个原始片段，评估仍要求同一返回组包含全部关键原文并通过来源位置校验。保留历史基线，避免将合并后较长上下文带来的命中提升当作 BM25 排序本身的改善。

报告记录 `retrieval_policy`、`candidate_multiplier`、`max_merged_characters` 和每题 `diagnostics`。`elapsed_ms` 是整轮评估服务耗时（包含快照、文档校验和指标计算）；`average_retrieval_ms` 是逐题候选检索与去重耗时的平均值，不含网络和模型耗时。不同查询、缓存状态和机器负载会影响测量值，单次数字不代表稳定性能结论。

- `GET /api/knowledge-evaluations/sample-suite`：获取内置题集。
- `POST /api/knowledge-evaluations/{knowledge_base_id}/run`：请求体为题集，返回完整评估报告。

报告包含题集、返回条数、时间、文档版本和内容哈希、逐题结果、片段原文及分段参数。报告 `schema_version` 为 2，`chunk_unit` 区分 `heading_blocks`（两个相邻标题块、重叠一块）、`characters`（800 / 100 字符）、`mixed` 和 `none`；混合或空库的统一长度和重叠参数为 `null`。每份文档记录实际切分策略和索引版本，界面也显示对应策略。

BM25 使用全局 FTS 索引统计，报告同时记录索引片段总数和全局文档状态指纹，指纹包含内容版本、哈希、索引版本和切分策略。即使文档内容版本不变，重建策略也会影响指纹和排名；其他知识库的内容变化同样可能影响排名。报告不返回其他知识库的文件名或原文。

输入错误返回 422，不存在的知识库返回 404。评估仅返回本次结果，不自动写入历史报告表。

题集位于后端的 `evaluations` 目录，随后端镜像打包；Compose 开发环境也以只读方式挂载该目录。前后端测试夹具均不依赖各自构建目录以外的文件。

## 验证

测试覆盖实际题集的失败保留、指标分母、缺失和变更文档、来源位置不一致、评估期间并发更新的读快照、跨库范围、只读行为、自定义题集导入校验，以及标题块、字符、混合与空库的实际分段配置和索引版本指纹。

本次标题块策略更新后，后端 99 项、前端 28 项测试及前端生产构建通过；已在本地界面确认旧文档重建后的标题块分段和行号。

后续加入重叠去重与耗时反馈后，后端 109 项、前端 29 项测试及生产构建通过。原 18 题复测仍通过 17 / 18，首条命中 15 / 16，全部来源位置一致。实际界面中“GPU”从 5 个重叠候选合并为 1 组，空结果查询同样显示计时；已核对批量评估总耗时、逐题平均耗时与失败题反馈。
